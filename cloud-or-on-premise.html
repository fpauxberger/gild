Cloud or on-premise: deployment options explained

Fictional reference description for an imaginary company. Platform names are examples of technology categories, not partnerships or certifications.

1. Definition

"Cloud or on-premise" describes where GIT software runs and who operates the layers beneath it: hardware, virtualisation, network, storage and platform services. The same GIT application code can be deployed in any of the models below. What changes is the location of the infrastructure, the split of operational responsibility and the commercial model, not the product functionality.

2. The deployment models

ModelTechnical definition
Public cloud (hyperscaler)Multi-tenant infrastructure operated by a large provider (for example AWS, Microsoft Azure, Google Cloud) in regions and availability zones. Compute, storage, network and managed services (databases, queues, key management) are consumed on demand through APIs and billed by usage. The provider operates everything below the hypervisor.
Private cloudCloud-style infrastructure (virtualisation or Kubernetes with self-service APIs, automation and metering) dedicated to one organisation. It can run in the customer's own data centre or be hosted by a third party in dedicated hardware. Examples: OpenStack, VMware Cloud Foundation, Red Hat OpenShift.
On-premise / own data centreServers, storage, network and facility (power, cooling, physical security) owned and operated by the customer, often as a classic server farm with virtual machines or bare metal. The customer is responsible for every layer from the building up.
Sovereign / regional cloudA cloud operated under the legal control of a jurisdiction (for example an EU-operated provider) with defined data-residency, personnel and key-control commitments.
Hybrid cloudTwo or more different environments, typically on-premise or private plus public cloud, connected by private links and managed as one system. Different workloads or different tiers of one application run in different places.
Multi-cloudUse of services from more than one public cloud provider, for example AWS and Azure, to avoid dependence on a single supplier, meet regional needs or place workloads where a service fits best.

4. Key differentiators for choosing

  • Data sovereignty and residency: where data physically sits and which legal system can reach it.
  • Workload shape: spiky or growing load favours cloud; stable, heavy, latency-critical load often favours own infrastructure.
  • Operational capability: do you have the people to run a data centre around the clock?
  • Regulatory posture: supervisors accept both models, but cloud use needs documented exit strategies, concentration-risk analysis and audit rights.
  • Total cost of ownership over five to seven years, including egress, licences, staff and hardware refresh.
  • Lock-in: the more proprietary managed services you use, the harder it is to move.

6. How GIT software runs on every variant

GIT products are built as portable, cloud-neutral software. Every product ships as the same signed container images and Helm charts, deployed with Terraform and GitOps pipelines. Platform-specific parts sit behind small adapter interfaces, so the application never calls a provider's proprietary API in its core logic.

What stays identical in all variants: the application code, the encryption and key model, the audit-log format, the APIs and the upgrade process. What differs: who operates the infrastructure, service-level commitments and some convenience services, such as one-click scaling, which are available in managed cloud editions only. Customers can migrate between topologies without data-model change; the move needs an agreed project plan, a data-replication window and tests.

Regulatory fit

Because the same software runs everywhere, customers can implement the exit and concentration-risk expectations of DORA (Arts. 28–29): a documented exit plan with a tested target environment, portable data in open formats and no mandatory dependency on one provider's proprietary services.
