Open APIs at GIT

Fictional description for an imaginary company. External links lead to the public pages of the named organisations; no partnership or endorsement is implied. CNCF project maturity levels change over time, so check the CNCF project list for current status.

1. Definition

An Open API at GIT is an interface that is (a) publicly documented with a machine-readable specification, (b) built on open standards rather than proprietary protocols, (c) versioned with a published compatibility policy, and (d) usable by any developer with standard tools, with no mandatory GIT-specific client. Specifications and software development kits are published under licences approved by the Open Source Initiative (OSI); see the Open Source Definition for what that means. Every function available in the GIT user interface is also available through the API (API-first principle).

3. API security

  • Authentication and authorisation: OAuth 2.0 and OpenID Connect, with fine-grained scopes per product and tenant; financial-grade profile (FAPI) for payment and account data.
  • Sender-constrained tokens: mutual TLS-bound tokens (RFC 8705) or DPoP (RFC 9449), so a stolen token cannot be reused.
  • Policy enforcement: authorisation decisions evaluated as code with Open Policy Agent; rate limits, quotas and schema validation at the gateway.
  • Integrity: optional JWS-signed requests and responses for non-repudiation of payment instructions; idempotency keys prevent duplicate bookings.
  • Auditability: every call carries a trace ID and is written to the tamper-evident audit log (see Secure by design).

Why this matters: open standards and community-governed components mean no single vendor controls the interface, customers can inspect and replace parts, and the same API stack runs unchanged on any hyperscaler or on-premise (see Cloud or on-premise). GIT also contributes back: the OpenAPI and AsyncAPI specifications and the client SDKs (Java, Python, TypeScript, Go) are published under the Apache License 2.0 in a public repository.

5. API lifecycle and compatibility policy

  1. Design-first: the OpenAPI/AsyncAPI file is written and reviewed before code; it is linted (for example with Spectral) in the build pipeline.
  2. Contract tests: generated mock servers and automated tests prove that the implementation matches the specification.
  3. Versioning: major version in the URL (/v1/); additive changes never break clients; breaking changes only in a new major version.
  4. Deprecation: at least 12 months notice, signalled with Deprecation and Sunset HTTP headers and in the developer portal.
  5. Errors: standard problem-details format (RFC 9457) with stable error codes; cursor-based pagination and consistent filtering.
  6. Sandbox and developer portal: synthetic data, interactive documentation, API keys per environment and a status page.

7. Regulatory and interoperability fit

  • PSD2 and open banking: account and payment interfaces compatible with Berlin Group NextGenPSD2 style APIs and strong customer authentication.
  • DORA (Arts. 28–30): open, documented interfaces and complete data export in open formats support the exit strategy and portability expected in ICT service contracts; API availability and performance are part of the contractual service levels.
  • GDPR: consent-scoped access and machine-readable export support data subject rights such as portability.
